河源短途出游微信小程序。当前直接在 `heyuan-v2.2` 内维护，名称与版本号不变；本次没有生成安装包、上传代码、提交审核或发布。

## 运行

在微信开发者工具中打开本目录并编译。无需安装 npm 依赖，无自建后台、数据库或云函数。主包提供首页、规划、景点列表、反馈等页面；景点详情与副图在 `pkg-detail` 分包中。

## 如何收到用户反馈

### 意见反馈：不用自建数据库

用户在首页点“意见反馈”→“打开微信意见反馈”，在微信原生页面填写并提交。开发者登录该小程序的微信公众平台，在反馈管理入口查看；具体栏目位置以当前后台为准。点击入口本身不会自动发送文字，旧版本本机记录也不会自动补发。

### 客服会话：绑定自己的微信号来接待

1. 登录该小程序的微信公众平台，进入“功能 → 客服”，添加自己的微信号为客服，并按页面完成绑定。
2. 从后台打开官方网页客服工具，使用所绑定的微信扫码登录，将客服状态设为在线。
3. 用户在本小程序“意见反馈 → 打开客服会话”发送消息，你可在客服工具查看和回复。

这是微信提供的小程序客服会话，并非直接给你的普通微信好友聊天发私信。无需在本项目里保存 AppSecret 或开发自己的消息数据库。本次接好了页面入口，未替你的账号绑定客服，也没有发送测试消息；实际接收需在绑定后用手机验收。

官方操作依据：[腾讯云：小程序客服消息接入实践](https://cloud.tencent.com/document/product/1301/107609)。

## 推荐模型（本机，不联网）

2026-11-04 起，自动规划不再用一个不可解释的合成分排序，而是拆成五个地点级特征：

| 特征 | 权重 | 怎么算 |
| --- | --- | --- |
| 兴趣匹配 | 0.30 | 分类命中记 1，标签或名称命中记 0.65，未限定兴趣记 0.72 |
| 地域匹配 | 0.22 | 同区县 1，同片区 0.55，跨区 0.08 |
| 新鲜度 | 0.26 | `e^(-去过次数/2)`，次数来自本机行为记录 |
| 同行人适配 | 0.14 | 强度契合 0.7 + 品类偏好 0.3 |
| 信息确定性 | 0.08 | 有坐标 0.5、有官方页面 0.3、有电话 0.2 |

方案分 = 地点均分 × 0.72 + 每天节奏契合分 × 0.18 + 参考路线加成 3 − 跨区换场 3.5/次。同行人只调整排序，不缩小可选范围；原有「区县、兴趣、天数、每天站数、游览时长、超时」全部仍是硬性筛选，模型不参与放宽。

权重为手调初值，依据是同条件下的排序是否符合常识，不是大样本训练结果。调参记录两处：参考路线加成从 6 降到 3、新鲜度权重从 0.24 提到 0.26，原因是「东源县·山水·去过万绿湖两次」的场景里，万绿湖原本仍排第一，与「去过就不再首推」的目标冲突。当前该场景下顺序为镜花缘、万绿谷、万绿湖。

`utils/events.js` 只在本机记录收藏、取消收藏、加入行程、移除、采用方案五类事件，最多 200 条，不含账号、位置或输入内容。清除小程序数据会一并丢失；它不参与分享，也不上传。

界面上每条方案会显示「匹配分」和最多三条理由（跨区时附一条扣分说明），底部注明分数由本机模型计算。

### 权重怎么调

```sh
npm run tune
```

`tools/tune-model.cjs` 会枚举 5 天数 × 3 交通 × 2 节奏 × 5 兴趣 × 8 范围共 1200 组条件，按四个可解释指标评价排序结果：时间填充率、区内凝聚度、方案差异度、信息完备率。搜索用坐标上升（每步 ±0.04，最多 3 轮），先过三条场景回归，再用指标排序。脚本不是机器学习，不编造标签，只回答一个问题：**换一组权重，这四项目标会不会真的变好**。

2026-11-04 实测结果：目标值 0.5368 → 0.5381，提升 0.25%，且兴趣权重顶到上界 0.40、人群权重压到下界 0.08。这类「顶边 + 微涨」通常是在拟合指标本身，脚本因此输出「不建议替换」，线上权重保持原值。单特征敏感性：任一权重 ±0.06，目标值变化都在 0.001 量级；新鲜度 −0.06 会直接让「去过两次不再首推」的场景失败，说明现在的权重主要由场景约束决定，不是由这四项指标决定。

同一套枚举还暴露了更要紧的问题：**补数据前 1200 组条件里只有 184 组能出方案（15.3%）**。拆开看，3–5 天步行全部无解是设计使然（步行只支持城区一日），其余主要是内容缺口——7 个区县 × 4 个兴趣共 28 个组合中，14 个完全为空，11 个只有 1–2 个地点。5 天自驾只有 12.5%。在这种情况下调权重没有意义，应先补地点。

2026-11-05 补齐数据后，同一套枚举实测 **328/1200 = 27.3%**（`node tools/coverage.cjs --solve`）：28 个格子只剩 2 个空、2 个稀疏。按天数拆分为 1 天 40.0%、2 天 36.7%、3 天 33.3%、4 天 14.2%、5 天 12.5%。可见 1 天受两个空格子与交通方式硬约束（步行仅城区一日、公交仅 5 个城区点）封顶，改善主要落在 2–3 天；4–5 天仍低，瓶颈已从「缺景点」转为「每日时长上限 + 地点不重复 + 步行/公交硬约束」，属于产品规则而非数据问题，不应靠继续堆景点解决。

判断一次调参能否上线的规则写在脚本里：目标提升 ≥1.5%、无权重触边、三条场景回归全过，三者同时满足才替换 `utils/model.js` 的 `WEIGHTS`。三条场景是：去过两次的地点不再首推、城区人文优先恐龙博物馆、带父母时古城优先于爬山。

## 手机验收路径

1. **优先验收关于页**：编译本目录，冷启动后直接进入“我的 → 关于 → 图片来源”，不要先打开景点详情。滚动到底，35 条记录的缩略图均应显示。此处副图记录也使用对应景点的主包封面作缩略图；实际副图在详情页查看。不要为测试清空已有行程或随手记。
2. 从首页进入龟峰塔、万绿湖等详情，检查封面、副图、左右切图和放大；弱网首次进入详情时也要检查。朋友圈单页应能展示，需写入或地图操作时引导进入小程序。
3. 万绿湖、霍山等地点点“在地图中查看位置”，确认地图名称与参考点对应；林寨古村等无可靠坐标地点应复制地点文字。打开地图失败时，确认可复制，取消则不改剪贴板。
4. 选和平县、1 天生成方案，采用后应回到第 1 天编辑，所有地点属于和平县。生成 5 天方案，修改第 5 天，再采用其他方案，确认从第 1 天展示，已保存行程仍在“我的”。
5. 预算展开，核对参考价、来源和“未计入”提示；起价不能视为价格上限。手填金额后预算同步变化，旧草稿金额不被默认参考价覆盖。
6. 详情 → 随手记 → 输入、保存，返回并重进确认仍在；分享详情后接收方不应看到你的随手记。检查手机键盘弹出时按钮和输入框可操作。
7. 首页 → 意见反馈，确认微信原生反馈页面能打开并在后台收到实际提交；绑定客服后由另一个微信发送测试消息，在客服工具确认接收和回复。详情反馈应带上景点名称。
8. 小屏手机检查底部按钮、安全区、五日标签及预算折叠；好友分享行程后核对日期、地点、费用和时间，确认没有夹带私人随手记。
