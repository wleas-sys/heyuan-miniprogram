## 一、测试方式

| 项 | 说明 |
|---|---|
| 框架 | Node.js 内置 `node:test` + `node:assert/strict`，无第三方测试依赖 |
| 夹具 | `tests/harness.cjs` —— **自研测试夹具**，用 `node:vm` 加载真实页面代码与真实 `utils` 依赖，提供 Mock 化的 `wx` API（存储、Toast、弹窗、定位、复制、震动、分享），并隔离微信运行时 |
| 被测对象 | 真实页面代码（`pages/*`、`pkg-detail/*/pages/*`）与真实业务模块（`utils/*`），不是复制品 |
| 失败注入 | 夹具支持按用例注入存储读取失败、写入失败、定位失败、复制失败等异常，用于验证降级路径 |
| 覆盖重点 | **异常分支与边界优先**：草稿损坏、存储写失败、权限不支持、包体积超限、数据未核实等 |

> `harness.cjs` 是这个项目里最花心思的一块：不 mock 业务逻辑，只 mock 宿主环境。这样测的是真实页面在真实微信 API 缺失或报错时的行为。

## 二、用例设计方法与实际体现

| 方法 | 在本项目中的体现 |
|---|---|
| **等价类划分** | 景点分类 / 区域 / 兴趣标签的有效与无效组合；天气、闭馆日、未知票价分别归入不同等价类 |
| **边界值划分** | 分页首屏 24 条的下界与上界；备份份数 5 份的上限与第 5 份；1–5 天规划的上下界；行程分钟覆盖值清空后的默认值回落 |
| **场景法** | 完整用户路径：搜索→筛选→清除；草稿读取失败→重试→修改→保存；损坏草稿→征询→备份→重建→继续编辑 |
| **错误推测** | 依据真实经历推测易错点：旧草稿引用已下线地点、分享链接的旧 dataVersion 回退、地图 API 不存在、反馈能力探测失败、副图下载失败、编辑页与详情页并发写同一份随手记 |
| **状态迁移** | 行程草稿在「读取失败 / 损坏 / 正常」三态间的迁移，以及每个状态下允许的操作集合 |
| **组合与冲突** | 「已填实付费用」与「参考预算」并存时以用户填写为准；同日万绿湖套票不得重复计入镜花缘 |

## 五、30 条代表性用例详解

> 挑的是**最能体现测试设计意图**的 30 条：异常分支、数据可信度、状态迁移、并发与降级。

| 编号 | 所属模块 | 用例标题 | 关键预期结果 | 优先级 | 来源文件 |
|---|---|---|---|---|---|
| TC-001 | 数据完整性 | 地点 id 唯一且为 ASCII slug | id 全局唯一且只含 ASCII 小写字母与连字符；文件名、路由与封面路径都以此为键 | P0 | data-integrity |
| TC-002 | 数据完整性 | 新增地点未核实的票价与开放信息都显式标注「待核对」 | 未经核实的条目必须带「待核对」标记，不允许以确定信息的形式出现 | P0 | data-integrity |
| TC-003 | 数据完整性 | 所有地点都不编造坐标 | `map` 要么为 null，要么同时具备数值型经纬度，不允许占位字符串 | P0 | data-integrity |

## 六、这套测试的三个特点

1. **只 mock 宿主，不 mock 业务。** `harness.cjs` 用 `node:vm` 加载**真实**页面代码与**真实** `utils` 模块，只把 `wx` 的存储、弹窗、定位、分享等宿主能力换成可控实现。测的是真实逻辑在真实异常下的行为。

2. **异常路径比正常路径测得更细。** 119 条里大量是"读取失败""写入失败""能力不支持""数据损坏""坐标非法"。原因很实际：这些是小程序最常见的线上问题来源，而普通测试往往只覆盖正常流程。

3. **用例标题写的是行为而不是函数名。** 例如「备份已满但其中包含当前原始草稿时直接复用，不受数量限制阻断」——读标题就知道期望什么，排查问题时不用先读代码。
